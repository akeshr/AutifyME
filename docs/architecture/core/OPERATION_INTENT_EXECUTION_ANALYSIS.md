# OperationIntent Execution Architecture - Gap Analysis & Solution

**Status:** Analysis Complete
**Created:** 2025-01-23
**Priority:** CRITICAL - Blocks Product Architecture Specialist execution

---

## Executive Summary

**Problem:** Product Architecture Specialist returns multi-operation OperationIntent, but PM has no way to execute it.

**Root Cause:** Phase 1.6 migrated PM to `write_data` tool (single-operation only), but didn't integrate multi-operation execution capability from deprecated `universal_crud_tool`.

**Solution:** Extend `write_data` to handle multi-operation WriteIntent (as designed in UNIVERSAL_DATA_ENGINE_DESIGN.md lines 688-1047), integrating OperationExecutor logic for atomic multi-table operations.

**Impact:** Unblocks Product Architecture Specialist migration and enables all future specialists to use structured multi-operation intents.

---

## Current State - The Gap

### What Works ✅

1. **Product Architecture Specialist** (`product_architecture_specialist.py` + prompt):
   - Constructs complete OperationIntent with multiple operations
   - Includes dependencies (`depends_on: [0, 1]`)
   - Includes entity refs (`entity_refs: {"family": 0}`)
   - Cross-references (`"family_id": "$ref:family"`)
   - Complete impact analysis
   - Self-review for completeness
   - Returns structured XML: `<operation_intent>{JSON}</operation_intent>`

2. **PM** (`project_manager.py`):
   - Has `write_data` tool for mutations
   - HITL enabled for `write_data`
   - Can delegate to Product Architecture Specialist

3. **Storage Layer** (Phase 1.1-1.5 complete):
   - Schema Engine: `inspect_schema` tool
   - Read Engine: `read_data` tool with aggregations, batch read, pagination
   - Write Engine: `insert_entity`, `update_entities`, `delete_entities`, `upsert_entity`, `patch_entity`, dry-run, validation

### The Gap ❌

**Specialist returns this:**
```json
{
  "intent_type": "create",
  "change_spec": {
    "domain": "product_catalog",
    "operations": [
      {
        "op_type": "insert",
        "table": "product_families",
        "new_entities": [{"name": "PET Jars", ...}],
        "entity_refs": {"family": 0}
      },
      {
        "op_type": "insert",
        "table": "variant_axes",
        "new_entities": [{"name": "Size", "family_id": "$ref:family"}],
        "depends_on": [0]
      },
      {
        "op_type": "insert",
        "table": "variant_values",
        "new_entities": [{"value": "500ml", "axis_id": "$ref:size_axis"}],
        "depends_on": [1]
      }
    ]
  },
  "execution_plan": {
    "steps": [...]
  }
}
```

**PM can only call this:**
```python
write_data(
    operation="insert",
    table="product_families",  # Single table only
    data={"name": "PET Jars", ...}
)
```

**Missing:**
- No way to execute multiple operations atomically
- No $ref resolution
- No dependency ordering
- No transaction wrapper across operations
- PM would need to orchestrate manually (complex, error-prone)

## Architecture Analysis

### Deprecated Tool Has the Logic

**universal_crud_tool.py** (DEPRECATED but functional):
- ✅ `OperationExecutor` class (lines 158-299)
- ✅ `execute_plan()` - Multi-step execution with ACID transactions
- ✅ `_resolve_dependencies()` - Topological sorting
- ✅ `_resolve_references()` - $step_N.field and $ref:name resolution
- ✅ Transaction wrapper with automatic rollback
- ✅ Strongly typed entity tracking (CreatedEntity, UpdatedEntity, DeletedEntity)
- ✅ Validation before execution

**Deprecation Notice Says:**
> "New tools provide: Simplified interface (no OperationIntent complexity)"

**BUT Design Doc Says (UNIVERSAL_DATA_ENGINE_DESIGN.md lines 688-1047):**
> "Multi-table transactions: ✅ **Enhanced** (auto-execution plan)"
> "Deep dependency chains: ✅ **Same power** (named dependencies)"
> "Topological sorting: ✅ **Same** (auto-generated)"
> "Foreign key references: ✅ **@name.field** (unified syntax)"

**Conflict:** Deprecation notice implies simplification, but design doc guarantees "ENHANCES all existing capabilities, loses NONE".

### Design Doc Vision

**WriteIntent Schema** (Design Doc lines 722-745):
```python
class WriteIntent(BaseModel):
    """Streamlined write intent - same power, less nesting."""

    goal: str         # Human-readable goal
    reasoning: str    # Why this change
    operations: list[Operation]  # Flat list (no ChangeSpecification wrapper)
    impact: dict      # Simplified impact (auto-validated)
    # execution_plan auto-generated by engine

class Operation(BaseModel):
    action: str  # "create", "update", "delete", "upsert", "query"
    table: str
    data: list[dict] | dict | None
    filters: dict | None
    updates: dict | None
    dependencies: list[str] = []  # Named dependencies
    returns: str | dict[str, int] | None  # Named result
    on_conflict: str = "error"
    cascade: bool = False
```

**Key Differences from Current OperationIntent:**
1. **Simpler**: No nested ChangeSpecification, no execution_plan required (auto-generated)
2. **Same Power**: Multi-operation, dependencies, references all supported
3. **Unified Syntax**: `@name.field` instead of `$ref:name` and `$step_N.field`
4. **Named Dependencies**: `dependencies: ["family"]` instead of `depends_on: [0]`

**Agent Usage Example** (Design Doc lines 693-719):
```python
write_data({
    "goal": "Create product family with variants",
    "reasoning": "User requested PET Bottles family",
    "operations": [
        {
            "action": "create",
            "table": "product_families",
            "data": {"name": "PET Bottles", ...},
            "returns": "family"
        },
        {
            "action": "create",
            "table": "variant_axes",
            "data": [
                {"name": "Size", "family_id": "@family.id"},
                {"name": "Color", "family_id": "@family.id"}
            ],
            "dependencies": ["family"]
        }
    ],
    "impact": {
        "creates": {"product_families": 1, "variant_axes": 2}
    }
})
```

**Multi-Table Transaction Capability** (Design Doc lines 952-970):
```python
execute_transaction(
    operations=[
        {"op": "insert", "table": "product_families", "ref": "family"},
        {"op": "insert", "table": "variant_axes", "depends_on": ["family"]},
        {"op": "insert", "table": "products", "depends_on": ["family"]}
    ],
    auto_resolve_deps=True  # Engine sorts by dependencies
)
```

## Solution: Integrate OperationExecutor into write_data

### Approach

**Extend `write_data` to handle BOTH:**

1. **Single-Operation Mode** (current - backward compatible):
   ```python
   write_data(
       operation="insert",
       table="products",
       data={"name": "PET Bottle", ...}
   )
   ```

2. **Multi-Operation Mode** (new - WriteIntent):
   ```python
   write_data(
       intent={
           "goal": "Create product family with variants",
           "reasoning": "...",
           "operations": [...],
           "impact": {...}
       }
   )
   ```

### Implementation Plan

#### 1. Extend WriteDataInput Schema

```python
class WriteDataInput(BaseModel):
    """Input schema for unified write_data tool."""

    # Single-operation mode (backward compatible)
    operation: Literal["insert", "update", "delete", "upsert", "patch"] | None = None
    table: str | None = None
    data: dict[str, Any] | list[dict[str, Any]] | None = None
    filters: dict[str, Any] | None = None
    updates: dict[str, Any] | None = None
    id: str | None = None
    conflict_fields: list[str] | None = None

    # Multi-operation mode (new)
    intent: dict[str, Any] | None = Field(
        None,
        description=(
            "Multi-operation write intent with goal, reasoning, operations list, impact. "
            "Enables atomic multi-table transactions with dependency resolution. "
            "Mutually exclusive with single-operation parameters."
        )
    )

    # Common parameters
    dry_run: bool = False
    validate_only: bool = False

    @model_validator(mode="after")
    def validate_mode(self) -> "WriteDataInput":
        """Ensure either single-operation OR multi-operation mode."""
        has_single = self.operation is not None
        has_multi = self.intent is not None

        if not has_single and not has_multi:
            raise ValueError("Must provide either operation/table OR intent")

        if has_single and has_multi:
            raise ValueError("Cannot mix single-operation and multi-operation modes")

        return self
```

#### 3. Integrate OperationExecutor Logic

**Create new module:** `tools/operation_executor.py`

```python
"""
Multi-operation execution engine.

Extracted from deprecated universal_crud_tool.py and enhanced for
Universal Data Engine integration.
"""

class MultiOperationExecutor:
    """
    Execute multi-operation write intents with ACID guarantees.

    Capabilities:
    - Multi-table atomic transactions
    - Dependency resolution (topological sorting)
    - Reference resolution (@name.field syntax)
    - Validation before execution
    - Dry-run preview
    - Strongly typed entity tracking
    """

    def __init__(self, storage: StorageInterface):
        self.storage = storage

    async def execute_intent(
        self,
        intent: dict[str, Any],
        dry_run: bool = False,
        validate_only: bool = False,
    ) -> ExecutionResult:
        """
        Execute multi-operation write intent.

        Args:
            intent: WriteIntent dict with goal, reasoning, operations, impact
            dry_run: Preview mode (no execution)
            validate_only: Validation mode (no execution)

        Returns:
            ExecutionResult with created/updated/deleted entities
        """
        # Parse intent
        operations = intent["operations"]

        # Validate completeness
        self._validate_intent(intent)

        # Dry-run mode
        if dry_run:
            return await self._preview_impact(operations)

        # Validation mode
        if validate_only:
            return await self._validate_operations(operations)

        # Execute with transaction
        return await self._execute_with_transaction(operations)

    async def _execute_with_transaction(
        self,
        operations: list[dict[str, Any]]
    ) -> ExecutionResult:
        """Execute operations atomically with dependency resolution."""
        # Sort by dependencies (topological order)
        sorted_ops = self._resolve_dependencies(operations)

        # Execute in transaction
        async with self.storage.transaction():
            context: dict[str, Any] = {}
            created_entities: list[CreatedEntity] = []
            updated_entities: list[UpdatedEntity] = []
            deleted_entities: list[DeletedEntity] = []

            for op in sorted_ops:
                # Resolve references
                resolved_data = self._resolve_references(op["data"], context)

                # Execute operation
                if op["action"] == "create":
                    result = await self.storage.insert_entity(
                        table=op["table"],
                        data=resolved_data
                    )
                    created_entities.append(CreatedEntity(
                        table=op["table"],
                        entity_id=result["id"],
                        data=result
                    ))

                    # Store in context for $ref resolution
                    if "returns" in op:
                        context[op["returns"]] = result

                elif op["action"] == "update":
                    result = await self.storage.update_entities(
                        table=op["table"],
                        filters=op["filters"],
                        updates=op["updates"]
                    )
                    updated_entities.append(UpdatedEntity(
                        table=op["table"],
                        count=result["count"],
                        entity_ids=result["ids"]
                    ))

                elif op["action"] == "delete":
                    result = await self.storage.delete_entities(
                        table=op["table"],
                        filters=op["filters"],
                        soft_delete=op.get("soft_delete", True)
                    )
                    deleted_entities.append(DeletedEntity(
                        table=op["table"],
                        count=result["count"],
                        entity_ids=result["ids"]
                    ))

            return ExecutionResult(
                success=True,
                created_entities=created_entities,
                updated_entities=updated_entities,
                deleted_entities=deleted_entities,
                execution_time_ms=...
            )
```
